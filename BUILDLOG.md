## Where AI helped
* Chose the architecture (api -> services -> repo), the outbox pattern for the email side effect, the token-bucket limiter, path-aware CORS.
* Wrote the migrations, the FastAPI app, the widget bundle/loader, demo pages, docker files, 57 tests, the probe runner and the docs.
* Ran the tests, the live probes (`scripts/run_probes.py`) and a headless-browser render; `EVIDENCE.md` is pasted from those real runs.

## Where the AI was wrong / what had to be fixed
1. **ETag compare bug** - `If-None-Match` handling stripped `W/` from the client's value but not the server's, so conditional GETs never returned 304.
   Caught by `test_config_is_public_small_and_cacheable`; fixed by normalising both sides in `app/api/public.py::_not_modified`.
2. A test that greps the widget for `innerHTML` failed because the AI's own *comment* contained the word; comment reworded.
3. First live-probe attempt failed because the server was started in a way that died with the shell; restarted detached. (Tooling, not product, but it shows why the probes are scripted.)

## Decisions to review and own (you may disagree)
* 404 instead of 403 for other tenants' resources (hides existence).
* Honeypot returns the **same 201** to bots; spam is counted, never stored.
* Raw IPs are not stored (keyed hash) - dashboards therefore can't show IPs.
* Geo results are not cached so the A/B fallback proof stays observable.
* Webhooks are a declared non-goal; email goes through a DB outbox + worker.
* Not verified here: the `docker compose` / Postgres run (no Docker in the build sandbox) and live `ip-api.com` / `ipapi.co` calls (mock geo was used for the proofs, as the brief allows).
